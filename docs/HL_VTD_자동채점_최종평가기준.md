# HL VTD 자동채점 최종 적용 기준 및 운영 안내

작성일: 2026-09-08
대상: VTD 2025.2 / HL_VTD 로컬 웹 평가기
접속 주소: `http://127.0.0.1:8765/`

## 1. 먼저 알아둘 점

- 사용자가 확정한 변경사항을 반영한 **팀 내부 평가기**다. 대회 공식 평가기와 동일함을 인증한 프로그램은 아니다.
- 기존 15개 항목 중 **차로 유지만 제외하여 14개를 평가**한다. 기존 웹의 표시 번호는 유지하므로 3번이 비어 있다.
- 500점부터 감점한다. 한 구간에서 동일 항목은 한 번만 감점하되, 경미에서 중대로 심화되면 추가 3점으로 합계 6점이 된다. 리스폰은 이 상한의 예외다.
- 채점 계산, 실시간 대시보드, 영상 중계, 기록 저장 기능은 구현되어 있다. 종료는 최신 사용자 결정에 따라 **마지막 체크포인트 도달**로 변경했다. **신호 연결 정보, 일부 보호구역 경계, 실제 VTD 수신 검증은 남아 있다.** 이 상태를 전체 자동채점 검증 완료로 표현하지 않는다.
- 데이터가 없으면 0점 감점/정상으로 확정하지 않는다. 화면의 `–`는 평가 대기 또는 자료 없음, `확인`은 해당 구간에 일부 미평가 샘플이 있음을 뜻한다. 3/6은 실제로 반영된 감점이며, 리스폰은 12/18 등도 가능하다.

## 2. 출처와 적용 우선순위

1. **사용자의 가장 최근 명시적 결정**: 이 프로젝트의 운영 기준으로 우선 적용한다.
2. **사용자가 전달한 운영측 질의응답**: OBB 기준, 중앙선 회피 예외 없음, 정지거리 2m 경계, 구간당 동일 항목 1회 감점.
3. **사용자 제공 `HL 평가기준.docx`**: `4. 항목별 평가 기준`, `5. 모든 항목에 공통으로 적용할 규칙`의 수치와 항목 정의. 이 DOCX는 공식 안내문 인용과 사용자 결정/구현 제안이 함께 있는 정리 문서이므로 모든 문장을 공식 규정으로 취급하지 않는다.
4. **측정 데이터**: `인터페이스 API.xlsx`, 제공 `viRDBIcd.h`, VTD 셋업 자료의 `Config/HLVTD/hl_vtd_config.json`, LivingLab XODR/시나리오 XML, 보호구역 YAML/CSV.
5. **구현 정책**: 공식 수치로 정해지지 않은 샘플 연결, 통신 공백, 객체 완전성, 위치 점프 검출 등. 아래에서 따로 설명한다.

이번 작업에서 새로운 법률 기준을 추가하지 않았다. 대회 영상 MP4는 화면 배치와 갱신 동작의 참고 자료이며, 감점 수치나 좌표의 출처로 사용하지 않는다.

### 수치 적용 주의

- 속도는 m/s 입력을 km/h로 환산하여 판정한다. 화면의 반올림된 소수 한 자리 값으로 채점하지 않는다.
- 2m **정확히**는 경미다. 51/70, 31/35km/h 등 속도 경계는 위 표의 포함 관계를 따른다.
- 지속시간은 연속된 유효 시뮬레이션 샘플로 측정한다. 시간 경계의 부동소수점 비교에는 1e-9초의 계산 오차 보정을 사용한다.
- ‘완전 정지=0’은 신호/보행자 정지 기준이다. **횡단보도 정차 항목만 별도로 1km/h 이하**를 사용한다.
- 적색점멸의 잘못된 정지 위치는 현재 **통과 시점에** 감점한다. 적색 정지 위치 위반은 정지 지속시간이 충족될 때 감점한다.
- 황색신호 통과를 별도 항목으로 감점하지 않는다. 적색 위반은 관측된 통과 프레임의 신호로 판정하므로 신호 전환과 통과가 같은 수신 간격 안에 일어나면 실제 VTD 로그와 대조해야 한다.
- 서로 다른 항목은 독립적으로 적용한다. 예: 보행자 대응 실패와 보행자 충돌은 각각 감점될 수 있다. 이 중복 정책은 DOCX의 **잠정 구현 정책**이며 운영측 공식 일치 확인은 별도다.
- 횡단보도 정차의 긴급정지 면제, 실선 회피 면제 같은 추가 예외는 자동으로 만들지 않았다. 중앙선 회피 예외 없음만 명시적으로 확정되어 있다.

## 4. 시작·종료·구간·총점

### 시작

1. VTD 상태 수신기와 제어 수신 감지기를 먼저 실행한다.
2. 제어기 PC에서 VTD PC의 TCP 9910으로 들어오는 유효 제어 패킷을 처음 관측하면 채점을 시작한다.
3. 조향·가속도·방향지시등이 모두 0이어도 유효 제어값이므로 시작한다. TCP 접속/SYN/ACK만으로는 시작하지 않는다.
4. 제어 없이 VTD를 Play하거나 차량만 움직이는 경우 시작하지 않는다.

인터페이스 API의 제어 패킷은 little-endian float32 조향 + float32 목표 가속도 + uint8 방향지시등, 총 9바이트다. 읽기 전용 감지기는 분할/합쳐진 TCP 데이터와 재전송을 처리한다. IPv4/Ethernet 또는 Linux loopback이 대상이며 IP 조각화/IPv6는 지원하지 않는다. 첫 명령을 놓치지 않도록 **제어기 연결 전에 감지기를 실행**한다.

‘수신 순간’의 구현 의미는 **VTD 호스트에 패킷이 도착한 시점**이다. 비공개 VTD 플러그인 내부의 소비/적용 콜백을 관측하는 것은 아니다. 주행시간 시작값은 가장 최근의 정상 RDB 시뮬레이션 시각(또는 직후 첫 프레임)에 맞춘다. 샘플 주기에 따른 시간 오차가 있으며 동일한 프레임 수준으로 현장 검증해야 한다. RDB 없이 오래된 제어 이벤트만 남은 경우 새 수신을 기다린다.

### 종료

- **설정된 경로의 마지막 체크포인트에 도달하면 `COMPLETED`로 종료한다.** 정지선·라바콘·후륜축 통과 여부는 현재 종료 조건에서 제외한다.
- `completion.mode: final_checkpoint`가 기본이다. 목표 위치는 `route.csv`의 `target_s_m` 위치이며, `target_s_m`을 생략하면 CSV 마지막 점을 사용한다.
- 현재 LivingLab 목표는 **X≈963.5114, Y≈-897.5979**, road **1928**, road S≈**84.8415m**다. 약 9.6m 더 앞의 정지선 후보는 종료에 사용하지 않으며 별도 확정이 필요 없다.
- 좌표가 소수점까지 정확히 일치해야 한다는 의미는 아니다. RDB Ego 위치 기준점이 목표점 **반경 1.5m 이내에 정상 진행방향으로 진입**하면 도달로 본다. `completion.tolerance_m: 1.5`는 기존 `config/control.yaml`의 `goal_tolerance: 1.5`와 맞추기로 **사용자가 확정한 값**이다. 다만 평가기와 제어기는 서로 다른 입력 시점·투영 방식을 사용할 수 있으므로 현장에서 같은 프레임에 GOAL이 되는지는 대조한다.
- 두 연속 샘플 사이의 이동 선분이 이 반경을 통과해도 도달을 인식한다. 경로 말단 부근 투영과 진행방향을 확인하며, ROAD_POS가 있으면 목표 도로·같은 방향 차로인지도 확인한다. 목표 원 밖의 옆 차로를 단순히 나란히 지나는 것만으로 종료하지 않는다.
- 중간 체크포인트/정지선, 후진 진입, 통신 공백·좌표 점프·Reset을 가로지르는 이동으로는 완주 처리하지 않는다. 이미 목표 원 안에서 첫 수신되거나 리스폰된 경우에는 도달 과정을 입증할 수 없으므로 즉시 완주 처리하지 않는다.
- 경로 설정이 없으면 체크포인트 종료를 사용할 수 없으므로 시작 시 설정 오류로 알린다. 기본 제한시간 900초에 도달하면 `TIMEOUT`으로 별도 종료한다.
- 기존 `finish_line` 방식은 명시적으로 선택한 이전 설정의 호환/회귀시험용으로만 남아 있다. 현재 기본 설정에는 적용되지 않는다.

### 구간과 점수

- 설정된 시작~끝 경로의 누적 경로 길이를 5등분한다. 차량이 실제 달린 총 거리로 5등분하지 않으므로 리스폰/우회로 구간이 임의로 바뀌지 않는다.
- `run_scenario.py`가 시작할 때 `/tmp/hl_vtd_active_assessment.json`으로 현재 시나리오 ID와 검증된 `route.csv`를 원자적으로 게시한다. 대시보드는 첫 제어 패킷에 이 프로필을 읽고, 당시 Ego를 현재 경로에 투영한 위치부터 경로 끝까지를 5등분한다. 프로필이 없을 때만 `assessment_rules.yaml`의 기본 경로를 사용한다.
- 기본 경로: `tools/dashboard/livinglab_route.csv`, 시작 경로 S≈3.58518, 끝≈841.99568. 첨부 Path01에서 생성한 차로 중심 경로이며 VTD PathRef TargetS보다 약 0.229m 짧다.
- 구간은 현재 경로 투영 위치로 결정한다. 경로에서 20m보다 멀어 투영 불가하면 마지막 구간을 유지하고, 첫 위치부터 구간 불명확하면 미설정으로 기록한다.
- 구간 분할 끝과 완주 목표는 동일한 최종 체크포인트를 사용한다. 최종 체크포인트가 변경된 시나리오는 경로 파일/목표 S도 함께 변경해야 한다.
- 초기 총점 **500 - 전체 감점 합계**. 미도달 구간의 100점을 따로 빼지 않는다. 음수 점수도 0으로 자르지 않는다. 다만 경로 미투영, 구간 미설정, 필수 메타데이터 또는 항목 입력 누락이 있으면 숫자를 공식 점수처럼 표시하지 않고 점수를 보류한다. 근거 검토용 `evidence_only_score`는 보고서 JSON에만 남긴다.
- 중대 위반 횟수는 구간·항목별 중대 확정 1회씩, 리스폰은 무료 횟수를 넘은 매회 1회씩 계산한다.
- 완주/시간종료 후 점수·주행거리·주행시간을 동결한다. Reset은 이전 로그를 보존하고 새 제어값을 기다리는 별도 세션으로 돌아간다.

### 신호 데이터

`metadata.stop_lines`에 정지선의 `id, begin, end, direction, road_id, lane_ids, signal_id, state_masks`를 지정해야 한다. RDB `TRAFFIC_LIGHT.state`는 참가자 API의 1=적색/3=녹색 같은 enum과 같지 않다. 실제 mask와 진행방향을 확인하지 않고 서로 대입하지 않는다. 좌/우회전 신호도 해당 진행방향에 맞춰야 한다.

이는 추가 채점 규칙을 결정하는 문제가 아니라 데이터 연결·검증 작업이다. 파일로 연결 후보를 찾을 수 있지만 실제 VTD를 실행해 신호 ID/상태 변화와 진행 차로의 신호를 대조해야 한다. 웹은 확인 도구일 뿐, 웹을 켜야만 신호 데이터를 기록할 수 있는 것은 아니다. 연결을 검증하기 전에는 해당 신호 항목을 임의로 감점하지 않는다.

사용자는 신호 **배너 표시**를 잠시 제외해도 된다고 허용했다. 이것이 적색/녹색/점멸 **채점에 필요한 신호까지 없어도 채점할 수 있다는 뜻은 아니다.**

### 객체·보행자

- `metadata.object_feed_complete`는 기본 false다. 평가 대상 보행자·차량·정적 장애물이 실제 Raw RDB로 빠짐없이 수신됨을 확인한 뒤 true로 바꾼다.
- false일 때 관측된 확실한 OBB 접촉은 감점할 수 있지만, 안 보이는 객체를 근거로 안전/무충돌을 확정하지 않는다. 녹색 정지 사유와 보행자 응답은 필요한 입력이 없으면 미평가한다.
- 보행자의 OBB가 횡단보도에 일부라도 겹치면 아직 횡단 중으로 본다. 완전히 벗어날 때까지 점유를 유지한다.
- 사용자의 보행자 보완은 ‘횡단보도에 보행자가 있는 경우 정지하고, 다 지난 후 진행’으로 적용했다. 보행자 없는 모든 횡단보도에서 무조건 정지하는 별도 규칙을 만들지 않았다.
- 녹색 미출발의 정당한 정차는 **Ego 전면 범퍼부터 예정 경로를 따라 전방 30m까지 만든 차량 폭 영역**과 다른 객체 OBB의 겹침으로 판정한다. 경로 투영이 없으면 현재 차량 진행방향의 직선 30m 영역을 대체 사용한다. 30m는 사용자가 확정한 기준이며, 곡선·교차로에서 생성 영역이 실제 주행 궤적과 맞는지는 현장 화면과 대조한다.
- 횡단보도 보행자 접근 거리 기본 30m는 별도의 구현용 공간 필터이며 녹색 미출발의 30m 기준과 혼동하지 않는다.
- 정당한 정차가 확인되면 녹색 타이머를 초기화하고, 사유가 사라진 뒤 다시 5/10초를 센다. 사용자 예외를 실현하기 위한 구현 정책이다.

### 리스폰·충돌 대체 검출

- VTD가 스스로 복귀시킨다. 웹은 차량 제어/리스폰 명령을 보내지 않는다.
- 프레임 간 이동거리가 `max(5m, (현재속도+이전속도)×dt+5m)`를 초과한 연속 수신 이동을 위치 재배치로 관측한다. 5m는 공식 리스폰 기준이 아닌 **임시 검출값**이다.
- 발생 횟수는 재배치 **직전 구간**에 기록한다. 작은 복귀, 통신 공백 중 복귀, 좌표 보정과 복귀의 구분은 놓치거나 혼동할 수 있다.
- 시간/프레임 역행은 현재 Reset으로 구분한다. VTD의 자동 복귀가 실제로 시간도 되돌리는지 현장에서 확인해야 한다.
- ‘보통 1초 이내 복귀’는 운영 설명이다. 1초가 지났다고 감점하거나 웹이 수동 복귀를 실행하지 않는다.
- 충돌은 2D OBB 겹침 및 높이 겹침으로 대체 관측한다. 복잡한 형상·급격한 움직임·샘플 사이 접촉은 오탐/누락 가능성이 있다. `RDB_CONTACT_POINT`를 차량 충돌 이벤트로 오해하지 않는다(타이어/노면 접점 정보).
- 실제 충돌/리스폰 정답 로그와 비교하지 않았으므로 **정확도 %를 제시할 근거가 없다.**

## 7. VTD PC에서 실행하는 방법

제어기 PC의 기존 TCP 9910 연결은 그대로 둔다. 대시보드는 **VTD가 실행되는 Linux 데스크톱 PC**에서 실행한다. 현재 개발 저장소의 `/home/jun/HL_VTD`와 실제 VTD PC의 설치 경로가 다르면 실제 경로로 바꾼다.

최초 준비:

```bash
sudo apt install python3-yaml ffmpeg x11-utils iproute2
cd /실제/HL_VTD
python3 tools/dashboard/check_environment.py --probe-rdb
```

터미널 1 — 웹/채점기:

```bash
python3 tools/dashboard/server.py --host 127.0.0.1 --port 8765 --rdb-host 127.0.0.1 --rdb-port 48190 --video-source window
```

터미널 2 — 위 서버가 출력한 **정확한 명령**을 복사하여 실행:

```bash
# 아래 XXXXX는 예시. 서버가 매번 출력하는 실제 경로를 사용한다.
sudo python3 /실제/HL_VTD/tools/dashboard/control_monitor.py --event-socket /tmp/hl_vtd_control_XXXXX/events.sock
```

- 패킷 읽기 권한이 필요한 작은 감지기만 sudo로 실행한다. **웹 서버 전체를 sudo로 실행하거나 Python 실행 파일 전체에 raw socket 권한을 부여하지 않는다.**
- 필요하면 감지기에 `--controller-ip 제어기IPv4주소 --interface VTD랜인터페이스`를 추가해 관측 대상을 좁힌다.
- 감지기는 9910에 접속/바인딩하지 않고 읽기만 한다. 제어기 IP/포트를 변경하거나 프록시를 거치게 하지 않는다.
- 웹 서버를 재시작하면 IPC 경로가 달라진다. 감지기도 새로 출력된 명령으로 재실행한다.
- 같은 PC의 브라우저에서 **`http://127.0.0.1:8765/`**를 연다. 포트 없는 `http://127.0.0.1/`가 아니다.
- 연결/평가 상태 영역에서 RDB와 제어 감지기 연결을 확인한 후 VTD Play 및 제어를 시작한다. 위 프로세스들이 켜져 있어야 자동으로 시작·갱신된다.

### 실시간 영상

- 같은 X11 화면 세션의 `mainRS`와 `birdRS`를 서로 다른 창 ID로 찾아 FFmpeg로 캡처하고, 웹에서 개별 또는 동시 표시한다. mainRS에만 `cam1`, `igVisualBroadcast` 순서의 명시적 fallback을 허용한다. 기본 목표는 화면별 10fps이며 보장 속도가 아니다.
- VTD와 브라우저가 같은 PC여도 렌더링 창/FFmpeg/화면 접근 권한이 준비되어야 한다. 닫힘·최소화·다른 DISPLAY·Wayland 환경에서는 캡처가 안 될 수 있다.
- VTD RTSP 송출이 이미 준비된 경우 다음으로 대체 가능하다:

```bash
python3 tools/dashboard/server.py --host 127.0.0.1 --port 8765 --video-source rtsp --mainrs-rtsp-url rtsp://127.0.0.1:8554/main --birdrs-rtsp-url rtsp://127.0.0.1:8554/bird
```

- `/api/video/mainrs/status`와 `/api/video/birdrs/status`는 각 화면의 최근 실제 JPEG가 들어온 경우에만 LIVE로 표시하며 실제 X11 창 title/ID/geometry를 함께 제공한다. 기존 `/api/mainrs_status`는 mainRS 호환 주소다. 미송출 시 스트림 API의 503은 영상 대기 상태이며, 과거의 API 미구현 404와 다르다.
- 영상과 채점 데이터는 독립된 연결이다. 영상이 나온다고 채점 입력이 모두 준비된 것은 아니다.
- 48190은 제공 셋업의 Raw RDB 출력 포트다. 실제 설치에서 다른 포트이거나 동시에 여러 클라이언트를 허용하지 않으면 평가기 전용 RDB 출력 설정이 필요하다. **9910을 RDB 포트로 지정하지 않는다.**
- 로컬 사용이 기본이다. `--host 0.0.0.0`은 필요 시 LAN에 공개하는 옵션이며 인증 없는 평가기를 인터넷에 노출하면 안 된다.

## 8. 시나리오가 바뀔 때

- 현재 기본 설정은 첨부 LivingLab Path01 기반이다. **RDB만으로 현재 실행 중인 XML/경로를 자동 식별하는 기능은 없다.**
- 같은 지도에서 주변 객체만 바뀌면 객체 ID를 고정하지 않고 해당 프레임의 객체로 평가한다.
- 경로가 달라지면 `route.csv`, `start_s_m`, `target_s_m`을 바꿔야 한다. 종료 목표는 그 경로에서 가져오므로 별도 종료 정지선 지정은 필요 없다. 지도가 바뀌면 XODR, 보호구역, 신호 연결도 해당 지도 것으로 교체한다.
- 별도 설정 파일을 만들어 `--assessment-config 경로/시나리오별.yaml`로 실행할 수 있다. 평가 코드를 매번 고칠 필요는 없다.
- 웹의 ‘기록 조회 시나리오’ 메뉴는 과거 CSV 조회용이다. 이 메뉴를 바꾼다고 VTD 시나리오나 실시간 채점 경로가 변경되지 않는다.
- 현재 설정의 마지막 체크포인트가 실제 시나리오의 최종 목표인지 확인한다. 도로 끝이나 가장 가까운 정지선을 임의의 대체 목표로 사용하지 않는다.

## 9. 로그·점검·검증 범위

세션마다 `output/assessment/<session_id>.jsonl`에 설정 사본, 시작 근거, 프레임 측정, 관측 사건, 감점 변경, 종료 결과를 저장한다. 기존 실행 기록을 삭제하지 않는다. 관측 사건과 실제 감점은 별도 기록이다. 주행 중 화면의 ‘결과 상세’에서 현재 판정과 미확정 정보를 확인한다.

이 JSONL은 전체 RDB 녹화 파일이 아니다. 기존 CSV 이력 선택기에서 새 JSONL 세션을 재생하는 기능은 아직 없다. 상단 ‘이력/관리자’ 텍스트는 참고 UI 표시이며 실제 사용자 인증/관리 시스템은 구현 범위가 아니다.

Pause 중 같은 시뮬레이션 시각은 누적하지 않는다. 0.5초를 넘는 샘플 공백, 명시적 수신 끊김, Reset, 좌표 점프 사이에는 위반 지속시간과 주행거리를 보간하지 않는다. 시뮬레이션 시간이 전진한 수신 공백은 전체 경과시간에는 포함된다. 완료 후 데이터 수신은 계속될 수 있지만 해당 세션 점수는 동결된다.

개발 환경 검증 명령:

```bash
python3 -m unittest discover -s tests -p 'test_*.py'
python3 tools/dashboard/check_environment.py --probe-rdb
```

개발 테스트로 속도/거리/시간 경계, 중복 감점/격상, 리스폰 누적, Reset/Pause/수신 공백, 첫 제어값 시작, 분할/재전송 TCP 제어 패킷, 마지막 체크포인트 도달/샘플 사이 통과/후진·순간이동 오판정 방지, 직선·곡선 경로의 전방 30m OBB 출발 방해 예외, 이전 종료선 방식의 호환, 보호구역 연결/좌표 복원/원본 보존, 횡단보도 추출, RDB 수신, HTTP 응답, 공유 JPEG 중계를 검사했다. 2026-09-10 현재 전체 Python 회귀 테스트 **163개 통과**(그중 대시보드 **88개**). **실제 VTD PC의 제어→RDB→영상→웹 전체 경로를 주행 검증한 것은 아니다.**

이번 개발 WSL에서 홈페이지·상태 API·기준 MD API는 HTTP 200을 확인했다. 현 환경은 Raw RDB 포트 연결 거부, FFmpeg 미설치 상태였으며 이를 연결 대기로 표시한다. 이 결과는 실제 autonav VTD PC의 설치 상태를 대신 확인한 것이 아니다.

### 실제 VTD 실행 후 확인 가능한 범위

VTD와 웹을 실행한 PC에서 이 저장소·프로세스·로그에 접근할 수 있으면 다음을 확인할 수 있다. 단순 정상 주행 한 번만으로 모든 판정의 정확성을 확정할 수는 없고, 정상·경미·중대 사례를 의도적으로 재현해야 한다.

| 확인 대상 | 실행 후 확인 방법 | 확인 한계/필요 조건 |
|---|---|---|
| 신호 매핑 | 정지선 앞 동일 차로에서 실제 RDB 신호 ID와 mask 변화를 적색·녹색·적색점멸 화면과 대조 | 각 신호 상태가 실제로 나타나는 시험이 필요. 매핑 전에는 9·10·11번을 확정 채점하지 않음 |
| 시나리오별 경로 | 실행 XML/경로 파일, RDB 주행 궤적, 마지막 체크포인트·5등분 구간을 함께 대조 | `run_scenario.py`의 실행 프로필로 자동 연결. 스크립트를 거치지 않는 외부 제어기는 현재 경로를 명시해야 함 |
| 객체 수신 완전성 | 차량·보행자·정적 장애물·신호등을 배치한 알려진 시나리오의 객체 목록과 Raw RDB 수신 목록 비교 | 일부 객체가 보이는 것만으로 ‘전부 수신’을 증명할 수 없음 |
| OBB 충돌·전방 30m 예외 | 접촉/비접촉, 진행영역 안/밖 사례를 각각 재현하여 JSONL 사건과 화면 비교 | 실제 물리 충돌 정답 또는 운영 화면과 비교해야 정확도 판단 가능 |
| 리스폰 | 같은 구간에서 1·2·3회 자동 리스폰을 발생시켜 무료/–6/–12와 귀속 구간 확인 | 통신 공백·Reset·작은 위치 보정 사례도 별도 시험 필요 |
| 후륜축·범퍼·보호구역·횡단보도 | VTD 확대 화면의 경계 통과 프레임과 평가기 좌표/활성 상태 비교 | 차량 치수와 RDB 기준점이 실제 Ioniq 6 설정과 같아야 함. 보호구역 15·28은 자료 보완 전 미평가 |
| 실시간 영상 | VTD mainRS와 birdRS 창을 함께 띄운 뒤 웹의 개별/동시 화면, 실제 창 title/ID, LIVE 상태, 지연·끊김 복구 확인 | 해당 창이 최소화되거나 X11/FFmpeg 캡처 대상이 틀리면 그 화면만 나오지 않음 |

검증을 요청할 때는 대시보드 서버 콘솔, `python3 tools/dashboard/check_environment.py --probe-rdb` 출력, `/api/live` 결과, 해당 세션 JSONL을 유지한다. Codex가 같은 VTD PC 세션에 접근할 수 없으면 이 네 자료와 문제 시점 화면을 전달해야 한다. 검증은 RDB·로그·화면을 읽는 방식이며 제어기 코드나 시나리오 원본을 수정할 필요가 없다.

### 현장 인수 시험

1. 제어 감지기/Raw RDB/영상 모두 연결. 기존 제어기에 영향이 없는지 확인.
2. Play만으로는 시작되지 않음. 첫 0 제어값에서도 시작. 감지기가 늦게 켜진 경우는 별도 재시험.
3. Ego 차량 치수·후륜축/범퍼 위치·5구간 경계·마지막 체크포인트 좌표와 1.5m 도달 범위를 화면과 대조.
4. 14개 항목의 정상/경미/중대 사례와 같은 구간 반복/다음 구간 재발을 대조. 미평가를 정상으로 세지 않음.
5. 보호구역 보류 15·28번 범위 확인, 정지선↔신호 및 mask 연결, 모든 평가 객체 수신 확인.
6. 자동/수동 리스폰 각 구간 1·2·3회 시험. 통신 끊김/좌표 보정과 구분되는지 확인.
7. 마지막 체크포인트 정상 도달로 완주/점수 동결. 중간 목표·후진·순간이동·목표 원 밖 통과는 완주 아님. 실제 제어기가 선택하는 최종 접근 차로/정차 위치에서도 도달을 인식하는지 대조.
8. Pause/Resume, Reset, 시간초과, 영상 끊김/복구 및 기존 기록 보존 확인.

## 10. 핵심 코드 위치

- `tools/dashboard/server.py`: 로컬 HTTP, Raw RDB/영상/제어 감지기 연결.

- `tools/dashboard/live_assessment.py`: 세션, 측정, 구간, 기록, 화면용 결과.

- `tools/dashboard/assessment_rules.yaml`: 속도, 경로, 차량, 체크포인트 종료, 메타데이터 설정.
- `tools/dashboard/route_assessment.py`: 경로 투영 및 마지막 체크포인트 도달 판정.
- `tools/dashboard/map_features.py`: 실제 횡단보도 및 정지선 후보 추출.
