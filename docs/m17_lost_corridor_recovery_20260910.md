# M17 경로 상실 복귀 — 1단계 수정

## 현재 상태: 2단계 중앙 선호 롤백 적용

후속 사용자 요청으로 중앙 이탈 비용, 중앙 복귀 전용 탐색 트리거/타이머,
추가 경로 교체 조건 및 전용 helper를 제거했다. 안전한 기존 로컬 경로는
위험 발생 또는 경로 연장 필요가 없는 한 유지하는 조건으로 되돌렸다.
아래 1단계의 경로 상실 복귀 트리거, 짧은 출발 주행면, 게이트웨이 연결 확인,
안전한 복귀/정착 구간, 복귀 경로 캐시와 저속 제한은 유지했다.
신호·보행자·비상제동 및 주행 속도 설정은 변경하지 않았다.

아래 VTD 기록은 롤백 **전** 1단계 실행이다. 롤백 후 새 VTD 실행 결과로
해석하면 안 된다. 새 중앙 유지 방식이나 실선 검사 강화는 아직 구현하지 않았다.

롤백 후 검증: 실행 파일 빌드 성공, `no_cosmetic_replan` 및
`lost_corridor_recovery`를 포함한 집중 테스트 5개와 안전 유지 부분집합 12개 통과.
원본 정지 장면을 다시 재생한 `after_center_rollback`에서도 154점의 동일한
4480 → 766 복귀 경로가 생성됐고, 여유 0.30m 안전 검사 통과/재시도 포함
약 1.10초였다. 새 VTD 주행은 이번 롤백 단계에서는 실행하지 않았다.

## 작업 순서

사용자 요청에 따라 우선 복귀 기능을 수정하고 검증한다. 직전의 중앙 선호
변경은 이 단계에서는 유지한다. 사용자가 복귀를 확인한 뒤 중앙 선호 변경만
선택적으로 롤백한다. 다른 기존 변경 전체를 git 원상복구하지 않는다.

## 원본 로그에서 확인한 현상

`output/verification/M17/m17_rviz/run.csv`에서 115.037초에 Ego가
173:1에서 4480:-1로 이동한다. 약 120.277초부터 같은 위치
(646.8562, -100.4688)에 정지한다. 저장한 장면은 635.2782초다.

이 미션의 마지막 구간은 173 → 766 → 174 → 781 방향이며 4480은 정식
허용 차선이 아니다. 해당 위치에서 766 중심선까지 약 2.42m다.
`stored_precomputed_path_forced`가 실행돼 목표 속도는 1.5m/s로 남아도,
`active_path_present=0`, `plan_valid=false`이므로 제어 명령은 -4m/s²다.
양의 목표 속도만으로 유효한 경로를 대신할 수 없다.

기존 로컬 탐색은 장애물 또는 활성 회피 경로의 연장 필요를 기준으로 시작한다.
경로 자체를 잃고 장애물 트리거도 없다면 복귀 작업이 시작되지 않는다.
투영 실패 후 `world.inputValid`까지 false가 되면 더 뒤의 탐색 진입점도 막힌다.

## 이번 수정

1. 실제 위치/지도 정보가 유효하지만 추종 경로가 없거나 떨어져 있는 경우를
   독립 복귀 트리거로 추가했다. 활성 경로 투영 실패 처리보다 먼저 실행한다.
2. 기존 코리더 → 확장된 복귀 지점 → 제한된 주변 주행면 탐색 순서를 유지한다.
   마지막 단계에서는 현재 차량이 이미 있는 도로의 짧은 출발 구간도 허용한다.
   현재 차선의 뒤쪽 차체 길이, 앞 40m 이내/반경 45m 범위이며 전역 권한은 변경하지 않는다.
3. 가까운 공식 차선 중 게이트웨이로 연결되는 차선에 접속 후보를 만든다.
   접속 길이는 6/8/10/12/14/16/20/24/28/32/35m를 비교한다.
   거리와 곡률을 비교하므로 단순 유클리드 최근접 도로에 강제로 붙이지 않는다.
4. 전체 미션을 가로막는 먼 트럭 때문에 접속 자체까지 거부되지 않도록,
   복귀 곡선과 최소 10m 정착 구간을 먼저 안전 검사한다. 이후 장애물은 기존
   회피 탐색이 이어서 처리한다. 최종 복귀점의 게이트웨이 연결성과 필수 단면
   통과 조건은 그대로 검사한다. 목표를 건너뛰거나 도달했다고 꾸미지 않는다.
5. 현재 위치 접속·차체 주행면·차선변경 허용·정적/동적 충돌을 통과한 결과만
   교체한다. 복귀 경로는 캐시하며 최대 5km/h로 추종한다. 신호·보행자 대기와
   동적 EBS 및 기존 정적 접촉 복구 정책은 변경하지 않았다.

일반 안전 회피 실패와 마찬가지로, 물리적으로 연결되는 경로가 전혀 없거나
필수 게이트웨이가 이미 뒤에 있어 합법적 전진 연결이 없는 경우까지 무조건
복귀를 보장할 수는 없다. 이 패치는 후진이나 임의 게이트웨이 건너뛰기를 추가하지 않는다.

## 정지 장면 재생 검증

근거: `output/verification/M17/m17_lost_corridor_20260910/`

- `stopped_snapshot.json`: 원본 정지 위치 및 당시 수신 객체 6개.
- `after_tracking`, `after_apron`, `after_short_join`: 중간 수정의 실패 기록.
  단순 트리거 추가/주행면 추가만으로는 충분하지 않았다.
- `after_safe_tail`: 현재 수정의 성공 기록. 154점, 약 34m, 4480에서 766으로 복귀.
  끝점 (613.93796, -108.90102), 766:-1 roadS=44.3043m.
  충돌 검사 여유 0.30m 통과, 재시도 포함 1.094초,
  성공 worker 약 19.16ms, 관측 재생 한 번의 폴링 최대 약 13.52ms.
  이것은 고정 관측의 경로 생성 검증이지 실차 추종/미션 완주 검증은 아니다.
- 신규 `lost_corridor_recovery`는 장애물 없이, 경로 투영이 무효이며,
  공식 코리더 밖의 인접 차선에 있는 상황에서 복귀를 검사한다.
  원래 허용 차선을 변경하지 않고 미션 단계를 건너뛰지 않는 것도 확인한다.
- 기존 코리더/제한 복귀/복구 후보 선택/중앙 선호를 포함한 5개 집중 테스트 통과.

## 새 VTD 실행

`output/verification/M17/m17_return_stage1_20260910/`

`--auto-vtd --inline-scenario --skip-source-sync --evidence --run-timeout 240`으로
실행했다. 기존 m17_rviz 실행기는 정상 종료한 뒤 중복 제어 없이 시작했다.
204.669초에 goal_reached=1, 프로세스 종료 코드 0, VTD Stop 완료.
패키지의 start_leg=2 그대로이며 P1부터 전체 미션을 검증한 것은 아니다.
plan_valid=0 프레임 0개, 기록상 객체 collision 프레임 0개다. 공식 감점 결과가 아니다.

이번 실행은 4480 진입을 재현하지 않고 766 → 174 → 781로 진행했다.
따라서 실제 주행 중 4480에서 돌아왔다는 증거는 아니며, 위 정지 장면의
고정 관측 복귀 성공과 구분해야 한다. 목표 직전 중첩 영역에서는 약 0.6초
207로 map match됐다가 781로 이동했다. 이것만으로 잘못된 회전 실행을 뜻하지는 않는다.

제어 송신 평균 19.921Hz, 간격 p95 85.63ms/최대 104.12ms,
GT 누락 17프레임, planning p95 35.91ms. 평균 20Hz에 가깝지만 주기 변동은 있다.

중앙 선호 단독 후보 교체는 87.109/88.230/89.430/91.269초에 네 번 있었다.
상태 준비와 경로 앞부분을 반복 재설정할 가능성이 있는 구체적인 흔들림 단서다.
실제 기준점의 선택 경로 추종 오차는 중앙값 약 0.93cm, p95 약 8.08cm였다.
지도 실선과 실제 기록 OBB 접촉은 이 새 실행의 해당 분석에서 검출되지 않았지만,
경로상 차체를 추정한 검사에서는 실선 여유 부족 표본이 19개였다.
이는 표본 접선으로 만든 근사 검사이므로 원래 후보 차체의 정확한 침범량이나
사용자가 경험한 다른 실행의 실선 접촉 여부까지 확정하지 않는다.
관련 파생 자료는 실행 폴더의 `lane_analysis.csv`, `lane_path_comparison.png`에 있다.

## 1번: 실선 접촉·흔들림의 원인과 다음 수정안

중앙 선호 비용은 전역 경로와 로컬 후보 양쪽 순위를 바꿨다. 안전한 기존 경로를
유지하던 조건에도 재탐색을 추가했다. 따라서 가까운 평행/중첩 연결 도로에서는
경로 선택과 교체 빈도를 바꿀 여지가 있다. 다만 원본에는 프레임 이력 전체가
없으므로 중앙 선호만이 4480 진입의 단독 원인이라고 단정하지 않는다.

또한 현재 `boundaryAllowed`는 road/section이 다른 두 표본을 바로 허용한다.
차체 주행면 검사 자체는 있으나, 이 조기 허용과 중첩 도로의 위치 분류만으로
실제 실선과의 여유를 보장할 수 없다. 동일 차선 내 중심 이탈 비용도 차체~실선
거리 검사와는 다른 기능이다.

권장 순서는 다음과 같다. 아래는 계획이며 아직 적용하지 않았다.

1. 복귀 확인 후 중앙 선호 비용/추가 재탐색/관련 후보 교체 조건만 롤백한다.
   이번 복귀 트리거·출발 주행면·안전한 짧은 정착 구간·캐시는 유지한다.
2. 전역 분기/게이트웨이를 먼저 고정한다. 중앙 선호가 다른 연결 도로를
   고르지 못하게 하고, 선택된 도로 위의 횡방향 경로 모양만 조정한다.
3. 연속 장애물 동안 기존 회피 측면을 유지한다. 장애물 묶음이 끝나고 다음
   구간에 여유가 있을 때만 같은 도로의 중심 복귀 후보를 비교한다.
4. 후보가 생길 때마다 교체하지 않는다. 현재 경로와 후보의 동일 구간을 비교하고
   충분한 개선/짧은 지속 확인/시작 조향 연속성을 만족할 때 교체한다.
   새 위험이 발생한 경우의 즉시 안전 재계획은 별도로 유지한다.
5. 실제 실선 형상과 전체 회전 차체 사이의 최소 거리를 별도로 확인한다.
   road ID가 바뀌어도 검사를 생략하지 않는다. 초기 여유 0.15~0.25m는
   검토값이며 폭이 좁은 구간·교차로 실제 표시·지도 오차로 검증해야 한다.
   이미 경계 밖에 있는 출발 상태를 무조건 탈락시켜 복귀까지 막지 않도록
   기존 침범을 줄이는 복귀와 새 침범을 구분한다.
6. 선택 경로 자체가 선을 밟는지와 제어 추종 오차로 차체가 밟는지를 분리 측정한다.
   이후에만 조향/룩어헤드 조정을 검토하며 먼저 제어 게인으로 가리지 않는다.
