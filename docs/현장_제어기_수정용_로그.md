# 현장 제어기 수정용 로그

## 1. 기존 출력과 분리

- 기존 터미널 상태 출력 함수·출력 주기는 유지한다. 추가 진단 내용을 터미널에 계속 출력하지 않는다.
- 기존 `--log`, `--decision-log`, `timing.csv` 형식은 유지한다.
- 새 `--diagnostic-dir`를 지정할 때만 **별도 파일** `diagnostics.jsonl`, `repair_decision.log`를 저장한다. 이 옵션만으로 기존 CSV·판단 로그를 켜거나 덮어쓰지 않는다.
- 제어 정책·가감속·조향·충돌 판정 조건은 변경하지 않는다. 새 로그는 비동기·고정 용량 큐를 사용한다. 메모리 복사·판단 문자열 작성·OS 스케줄링 비용은 0이 아니므로 실제 대회 PC에서 20Hz를 확인한다. 기존 CSV·명시적으로 켠 상세 로그·RViz의 비용은 그대로다.
- 로그 저장 실패만 `[diagnostics-error]`로 알린다. 진단 파일은 불완전할 수 있으므로 경고를 확인한다.

## 2. 실행

먼저 최신 소스를 빌드한다. 기존 실행 명령의 설정·경로 인자는 그대로 두고 아래 인자만 **같은 명령 뒤에** 추가하면 원시 수정용 로그가 별도로 저장된다.

```text
--diagnostic-dir output/repair_01
```

`output/repair_01`은 새 시도마다 `repair_02`처럼 바꾼다. 같은 파일을 덮어쓰지 않는다. 기존 명령만 실행하고 위 옵션을 생략하면 수정용 로그는 생성되지 않는다.

**GPT 전달용 소스·입력 스냅샷과 종료 후 자동 ZIP까지 필요하면** 대회장 매뉴얼의 갱신된 `comp_run 01`을 사용한다. 내부적으로 아래 구조의 명령을 사용한다.

```bash
python3 tools/diagnostics/run_field.py \
  --output "$COMP_DIR/run_01" --binary ./build/hl_vtd -- \
  --config config/network.competition.yaml \
  --control-config config/control.yaml \
  --map-config config/maps/living_lab.yaml \
  --vehicle-config config/vehicle.yaml \
  --path "$COMP_DIR/route.csv" \
  --checkpoints "$COMP_DIR/checkpoints.csv" \
  --scenario-id COMPETITION --run-id run_01
```

위 명령은 저장소 루트에서 실행한다. `$COMP_DIR`·대회 설정·경로는 매뉴얼에서 먼저 준비한다. `run_field.py`는 VTD 시나리오를 실행/초기화하지 않고 제어기만 실행한다. 기존 제어기 출력 내용은 화면으로 전달하면서 `console.log`에도 보존한다. 이 래퍼는 파일로 출력을 받아 전달하므로 직접 터미널 실행과 출력 버퍼링 시점은 다를 수 있다. 진단 원본은 별도 파일에 별도 스레드에서 저장하고 약 100ms마다 flush한다. 정상 종료 시 대기 중 기록을 비운다.

래퍼는 기본으로 `--log`, `--diagnostic-dir`, `--ready-file`, `--mission-output`을 지정한다. 중복 상세 파일의 동기 I/O를 피하려고 `decision.log`·`timing.csv`는 기본으로 켜지 않는다. 필요할 때만 래퍼의 `--` 앞에 `--legacy-decision-log`를 추가한다(추가 지연 가능). 제어기 자체의 기존 `--decision-log` 동작·형식은 바꾸지 않았다. 시작/종료 때만 `[field]`로 저장 위치를 안내한다.

**주행 중 PC 조작 금지.** 운영측의 시험 종료·조작 허가 후 필요할 때만 Ctrl+C로 종료한다. 정상 종료·오류 종료·래퍼 Ctrl+C 후 요약과 ZIP을 만든다. 전원 차단/SIGKILL/디스크 오류에서는 자동 포장을 보장하지 않는다.

## 3. GPT에 줄 파일

1. `run_01/GPT_BRIEF.md`: 증상, 최초·마지막 관측 프레임, 우선 확인할 소스 위치, 근거·미확인 사항.
2. `run_01/gpt_bundle.zip`: 위 요약 + 원본/발췌 로그 + 실행 전 소스·설정·경로·지도·Git 변경사항.

ZIP에는 `snapshot/tools/`의 실행·미션 생성·지도 계산 코드, `snapshot/tests/`의 테스트 코드와 로컬 시험 입력, `snapshot/scripts/`도 포함한다. 실행 후 이 파일들을 고쳐도 해당 시도의 복사본은 바뀌지 않는다.

- `REPRODUCE.md`: ZIP 내부 소스 누락 검사, 오프라인 빌드·로그 테스트 명령, 미션 입력 경로 확인 및 재현 한계.
- `environment.json`: 수집 도구의 OS·Python·NumPy·SciPy·PyYAML 버전. 전체 빌드 환경을 고정한 컨테이너는 아니다.
- 기존에 생성한 시도를 다시 포장해도 **그때 보존하지 않은 소스까지 사후 복원되지는 않는다.** 재현 안내에 누락 여부를 표시한다.

ZIP을 첨부하고 **실제 증상·남은 시간**을 말한다. ZIP 생성은 로컬 작업이며 자동 외부 업로드는 없다. 소스·설정이 포함되므로 전달 전에 공유 범위를 확인한다.

종료된 시도의 ZIP 재생성:

```bash
python3 tools/diagnostics/pack_field.py "$COMP_DIR/run_01"
```

직접 `--diagnostic-dir`만 사용한 폴더도 포장할 수 있지만 실행 전 소스 스냅샷은 사후 복원할 수 없다. 래퍼 강제 종료로 `.capture_running`이 남으면 **해당 제어기·작업이 실제 종료됐는지 확인한 후** 잠금 파일을 정리해야 한다. 실행 중인 시도는 포장하지 않는다.

## 4. 기존 요청 항목의 저장 위치

`repair_decision.log`는 기존 판단 이벤트 + 추가 진단 이벤트 중 제한된 양을 별도로 저장한다. 프레임당 후보 상세 최대 32개, 핵심 이벤트 최대 64개이며, 중복 `planning/frame_result`는 최종 JSON으로 대체한다. 이벤트 상세는 1,535바이트까지이며 잘림을 표시한다. 누락·축약 수는 `repair_health.json`에 남긴다. 기존 `decision.log`에는 추가 이벤트를 넣지 않는다. 두 원시 로그는 `frame`으로 연결한다. 해당 분기를 실행한 경우에만 그 판단 이벤트가 나온다.

| 요청 내용 | 별도 로그의 근거 |
|---|---|
| 프레임·실행시간 | JSON `frame`, `wall_s`, `process_wall_s`, `sim_s`, `dt`; 판단 로그 시간·frame |
| Ego road/section/lane/pathS/pathD/speed | JSON `ego` 전체 |
| 객체별 장애물 후보 검사·탈락 사유 | 판단 로그 `obstacle_scan` + JSON 전체 `objects` |
| 선택된 정적 장애물 ID·거리 | `blocker_selected`, 추가 `selected_distance` |
| 양쪽 목표 차선 조사 | 추가 `lane_topology/side_scanned`, 기존 `target_candidate_started` |
| 중앙선·반대방향 후보 탈락 | 추가 `adjacent_rejected`, 기존 위상 검증 이벤트 |
| 목표 차선 앞뒤 간격·종방향 속도·접근속도·TTC·판정 | `target_lane/gap_ttc_checked` + 추가 `gap_ttc_thresholds` |
| 목표 차선에 객체 없음 | `gap_ttc_checked`의 `no_object_matched_target_lane` |
| 다음 전역경로의 정확한 road/section/lane | 추가 `next_global_goal`, `required_forward_goal`; 미션 모드는 JSON `mission.target_road_section_lane` |
| 목표 차선→다음 경로 연결 결과 | `keep_route_connection_result`, `keep_route_rejected`, `keep_route_build_failed`; JSON `lane_change.reconnect_*` |
| 후보 OBB 검사 시간 범위 | `candidate_obb/full_path_checked`의 dynamic/static horizon·step |
| OBB 위험 객체·예상 TTC | 위 이벤트의 risk_object·predicted_ttc + JSON `planning`·객체 OBB |
| KeepTargetLane/ReturnToSource 선택 | `lane_change` 선택 이벤트 + JSON `lane_change.route_mode` |
| Prepare→Execute→Settle→None 전이 | `phase_transition` + JSON `lane_change.phase` |
| 복귀 위험 감속·대기 | `return_wait_changed`, JSON `waiting_return`·최종 목표속도·위험 객체 |
| 최종 정지·긴급제동·목표속도 | JSON `planning`은 계획 함수 반환 **후** 값; `control.nominal/safe`·송신 결과 |

최신 코드에 맞춰 추가 기록하는 내용:

- 수신 Ego/신호, 최종 World 관측 객체 최대 30개, OBB·위치·속도 유효성, 입력 누락·수신 대기. 중복되는 GT 객체 30슬롯 별도 기록은 생략한다.
- 제어 명령의 안전 제한 전/후 값, 변경 사유, 송신 완료/실패/수신전용 모드.
- 콜리더/게이트웨이 미션 구간·목표 차로·통과 관측 상태.
- 회랑 전역경로 revision·진행·승인 여부·막은 객체, 비동기 탐색 시작/완료/채택/폐기 이벤트.
- 로컬 대체 경로·재위치추정·경로 복귀·정체 복구 상태 및 기존 관련 판단 이벤트.
- 신호/정지 요청·대기 시간·진행 복구 override, 최종 추종 경로 샘플·조향·추종 대상 index.
- 연결/지도/미션/World/Planning 등 마지막 실행 단계, RDB 시각 연결 실패, 프레임 처리 시간.
- 실행 전 소스·설정·입력 해시, 바이너리 해시, Git HEAD/차이. 소스와 바이너리가 동일 빌드라는 보증은 별도다.

## 5. 해석·검증 한계

- 점수·공식 위반 판정·자동 코드 수정 기능이 아니다. 정상 신호 대기도 `ZERO_TARGET_WAIT`에 포함될 수 있다.
- OS의 TCP 송신 완료는 VTD 적용 ACK가 아니다. 차량이 안 움직이면 외부 제어 연결·Play도 확인한다.
- 무이동 2초/0.2m, 계산 100ms, 경로 거리 1m는 증상 발췌 기준일 뿐 제어 파라미터나 공식 규칙이 아니다.
- `sim_s=null`은 시뮬레이션 시간 미확인이다. 동결된 시뮬레이션 시간은 가속 제어 오류와 구별한다.
- 객체는 제어기가 받은 관측 범위다. 누락/폐기된 GT는 복구하지 못한다. 로컬 경로는 최대 17점으로 샘플링한다. 정지 요청은 최대 16개, 목표 차로는 최대 32개이며 전체 수를 별도 기록한다.
- 후보 경로별 모든 점·비동기 worker의 모든 내부 상태를 재현하는 완전 리플레이는 아니다. 관측 근거가 부족하면 추가 확인이 필요하다.
- 입력 요약·실행 단계·판단 이벤트는 고정 용량 메모리 큐에 복사한다. 최종 상태는 제어 명령 송신 **후** 복사하며 JSON 변환·저장·flush는 별도 스레드가 담당한다. 큐가 가득 차면 기다리지 않고 기록을 건너뛴다. 정상 종료는 큐를 비우지만 강제 종료·저장 오류에는 꼬리 기록이 없을 수 있다.
- 발췌는 선택된 오류의 시작/끝 프레임과 바로 전후 **관측 프레임을 통째로** 먼저 보존한다. 해당 프레임의 입력·처리 단계·최종 상태·송신 결과를 쪼개지 않으며, 그 프레임의 판단 이벤트도 모두 보존한다. 나머지 공간에 주변 기록을 넣는다.
- 일반 발췌 목표는 JSON 320개 기록·판단 이벤트 200줄이다. 핵심 기록만으로 한도를 넘으면 삭제하지 않고 한도 초과를 명시한다. 원본은 ZIP에 함께 남는다. 포장/업로드 시간은 실제 대회 PC에서 확인한다.
- 15분 안에 첫 수정으로 모든 문제가 해결되거나 완주한다는 보장은 할 수 없다. 수정 후 빌드·관련 테스트·재주행 근거가 필요하다.

## 6. 주기·누락 확인

종료 후 `GPT_BRIEF.md`에서 관측 평균 Hz, 최장 송신 간격, 55ms 초과 횟수, 수신→송신 시간, 진단 복사 시간, 큐 누락·이벤트 축약 수를 본다. 평균만 20Hz여도 긴 간격이 있으면 지터가 있는 것이다. 누락된 표본이 있으면 통계 역시 부분 관측이다.

`diagnostics.jsonl`의 `logger_status.final=1`과 `repair_health.json`의 `final=1`은 저장 큐를 정상적으로 비웠다는 뜻이다. `dropped_*`는 저장 지연에 따른 누락, `limited_*`는 프레임별 분량 제한, `truncated_*`는 긴 문자열 잘림이다. 누락 0이어도 VTD 동작이나 문제 해결을 보증하지 않는다.

## 7. 빠른 개발 검증

```bash
python3 -m unittest discover -s tools/diagnostics -p 'test_*.py' -v
cmake --build build --target hl_vtd field_diagnostics_tests --parallel 2
ctest --test-dir build -R '^field_diagnostics_tests$' --output-on-failure
```

테스트는 기존 판단 파일/시각화 이벤트 불변, JSON 기록, 원본 보존, 무이동·시뮬레이터 정지 구별, 오류/부분 로그 포장 등을 확인한다. 실제 VTD 연결과 대회 PC의 기록 부하는 별도 검증 대상이다.
