- 경로별 검증 여유를 저장해 비동기 결과 채택, 후속 추종, 복귀 연결, 다음 구간 인계와 재계획 판단에 전달한다. 운영 기본 여유는 변경하지 않는다. 좁은 여유 경로는 기존 저속 설정(5km/h)을 적용한다.
- 확장 탐색은 기존 비동기 전역 작업에서 실행한다. 탐색 상태 배열은 전체 지도 대신 활성 탐색 구간에만 할당하고, 기존 곡선 충돌 캐시·실패 재시도 제한·재탐색 억제를 유지한다.

## 결론

VTD 트럭 수신 실패가 아니라 **통과 가능한 횡방향 위치의 누락 + 로컬 탐색의 시작 연결 실패 + 대기 접근 경로가 재탐색을 억제하는 조합**이다. 장애물은 출발 프레임부터 인식되었다. 전역 탐색도 실행했으나 전체 경로 대신 트럭 뒤까지 접근하는 경로를 선택했다. 앞선 정체 탈출 수정은 이후 저속 접촉 진행을 허용했으며, 회피 경로 생성 결함을 해결한 것은 아니다.

## 1. 가능한 통로를 전역 후보가 표현하지 못함

`src/planning/local/corridor_lattice.cpp`의 `materializePrecomputedGatewayRouteStage`는 차선별 오프셋 상태가 3개다. 폭 2.9m, Ego 폭 약 1.88m, 차선 가장자리 여유 0.15m 조건에서 차선 중앙 대비 후보는 -0.36, 0, +0.36m다. 옆 차선 중앙과 그 차선의 오프셋으로 이동하는 곡선은 있지만, 경계를 걸친 채 중간 위치를 유지하는 상태가 없다.

관측 OBB로 계산한 0.05m 여유 조건의 공통 통과 위치는 해당 차선 중앙 대비 약 +0.731~+0.931m다. 이 값은 **차량 중심이 놓일 횡방향 구간**이며 통로 자체의 전체 폭이 아니다. 현재 전역 샘플에는 이 구간이 없다. 로컬 그래프의 5개 슬롯도 차선 내부 오프셋과 공유 경계 위치를 사용하므로 중간 간격 누락이 남는다.

실제 통과 가능성은 별도 진단에서 확인했다. 기존 전역 중심 경로를 참고하여 첫 두 장애물을 통과하고 원래 차선으로 복귀하는 구간 후보 2,304개를 만들고, **운영 코드 그대로의 `surfaceAndMarks`와 `stationaryPathClear`**로 검사했다. 차량 전체 footprint, 도로 범위, 차선 변경 허용, 장애물 OBB, 곡률을 모두 통과한 후보는 216개였다. 저장한 예시는 최대 횡이동 0.75m, 장애물 여유 0.05m, 최대 곡률 0.08644/m로 한도 0.17685/m 이하다.

검증 범위는 첫 두 장애물을 지나 차선으로 복귀하는 약 59m 구간이다. 새 전역 탐색 구현이나 게이트웨이까지의 새 전체 경로, 새 경로의 VTD 폐루프 주행 성공을 검증했다고 해석하면 안 된다. 0.75m는 결함을 입증하는 예시이며 수정할 상수가 아니다.

또한 현재 전역 검색은 nominal 여유 0.5m를 사용한다. 로컬에는 0.05m 단계가 있지만 전역에는 동등한 좁은 틈 탐색 단계가 없다. 단순히 전역 여유만 줄인 재생도 실패했으므로 여유 조정만으로는 해결되지 않는다.

## 2. 로컬 탐색은 출발점 연결에서 즉시 탈락

첫 Ego 위치와 지도 최근접 샘플 차이는 약 0.204m다. `searchLocalCorridor`의 첫 종방향 연결은 위치 차이가 0.15m를 넘으면 `generated=true`로 곡선을 요구한다. 바로 다음 샘플까지 실제 거리는 0.280246m인데 `curve`는 길이 3m 미만을 거부한다.

운영 소스의 임시 진단 복사본에 출력만 추가하여 확인한 결과:

```
from=240411 to=240412 generated=1 length=0.280246 geometry=0
```

따라서 이 시점에는 장애물 충돌 검사 이전에 로컬 탐색이 끊어진다. 실제 주행 기록의 첫 로컬 검색은 29.34ms, 확장 상태 6개, timeout=0, success=0이다. 계산 시간을 늘리는 것으로 해결되는 실패가 아니다. 작은 위치/방향 차이에 대해 충분한 길이의 실제 자세 연결을 탐색해야 한다.

## 3. 대기 접근 경로 채택 뒤 회피 탐색 기회가 줄어듦

0.416초에 전역 작업자가 `entrance_lane_queue_approach_built`를 반환한다. `success=1`이라는 작업 완료 로그는 **게이트웨이 전체 연결 성공이 아니라 안전한 대기 접근 경로 생성 성공**이다. RViz의 전역 경로 점 수 0은 실제 상태와 일치한다.

`prepareLocalCorridorFallback`은 대기 접근 경로가 선택되면 그 끝 너머를 물리 경로로 탐색하는 처리를 억제한다. 선택 경로 자체가 장애물 앞에서 끝나므로 장애물 검사 결과는 무한대(선택된 짧은 경로에는 장애물 없음)가 되고, 로컬 작업 필요 조건이 꺼진다. 실제 기록에서 첫 로컬 실패 뒤 11.016초까지 다음 로컬 작업 시작이 없다. 일반 단일 곡선 후보 탐색은 별도로 존재하므로 모든 계산이 중지되었다는 뜻은 아니다.

그 동안에는 대기 접근 경로로 전진하다가 정체 탈출이 작동한다. 이것이 처음부터 회피하지 않고 트럭으로 접근하고 접촉 진행하는 이유다. 같은 기록에서 전역 경로가 처음 표시된 것은 21.2954초다.

## 수정 범위

승인된 단계적 전역 후보 확장과 이를 채택·추종하는 데 필요한 검증 여유 전달만 적용했다. 초기 진단에서 제안했던 로컬 시작 연결 변경과 대기 중 로컬 탐색 억제 변경은 적용하지 않았다. 기존 게이트웨이 대기·복귀 및 신호 정지 정책을 유지했다.

## 다른 시나리오 영향 및 필요한 검증

공유 탐색 코드를 바꾸므로 영향이 있다. 후보 증가로 계산량과 선택 경로가 달라질 수 있으며, 좁은 여유 경로를 기존 nominal 검사로 재검사하면 다시 정지하는 오류가 생길 수 있다. 현재 경로가 이미 검증되어 있으면 유지하고, 필요한 경우에만 추가 후보를 열어 변경 범위를 제한한다.

- M20/M20-01: 유일 게이트웨이 앞 대기, 충분한 우회·복귀 공간이 있을 때만 통과 경로 채택, 다른 차선에서 게이트웨이 복귀 유지.
- M19/M19-01: 시작 연결과 곡선 채택 변화로 회전교차로 조향·경로 전환이 흔들리지 않는지 확인.
- M12: 회피 후 여러 차선 복귀가 필요한 게이트웨이 제한과 실선/다른 진출로 침범 거부 유지.
- 일반 회피: 단일 장애물, 서로 엇갈린 장애물, 차선 폭 변화/합류부, 후보 시작 위치 오차, 이동 객체, 비동기 탐색 중 객체 변화, nominal 경로 유지와 tight 경로 속도 제한을 검사.

앞선 정체 탈출 수정으로 실행한 M16은 474.817초에 goal_reached=1로 종료됐지만 접촉 기록 396프레임이 있다. 따라서 이것을 회피 문제 해결의 증거로 사용하지 않는다. 이번 변경의 실제 회피 동작과 접촉 감소는 사용자가 별도 주행 검증한다.
