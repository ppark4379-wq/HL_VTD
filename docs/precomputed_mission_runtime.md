# 사전 콜리더·게이트웨이 런타임 연결

`hl_vtd --checkpoints <CSV>`는 VTD 제어 연결 전에 다음 순서로 초기화한다.

현재 시작 연동은 Linux/POSIX 기준이며 Python3 + NumPy가 필요하다. C++ 빌드는 Boost 헤더(PropertyTree)와 스레드 지원을 사용한다. 런타임 생성에는 Qt·시각화 도구가 필요 없다.

1. 설정 XODR와 기존 샘플점 네트워크를 로드한다.
2. 실제 로드한 XODR의 차선 면·방향 그래프를 내보낸다.
3. `prepare_runtime_mission.py`가 갤러리와 같은 `whole_mission_corridors.Network`로 전체 미션을 생성한다. `route.csv`나 시나리오별 분기를 사용하지 않는다.
4. XODR/샘플점 manifest 해시, 체크포인트 순서, 도로 면·게이트웨이 연결과 다음 게이트웨이까지의 연결을 검사한다.
5. C++가 `complete_network.json.runtime_legs`를 읽고, 기존 guide 기반 미션 대신 주행 영역·목표로 적용한다. 실패하면 VTD 주행을 시작하지 않는다.

실행별 데이터는 `output/runtime_mission/startup-<PID>/complete_network.json`에 저장된다. 동시 초기화끼리 덮어쓰지 않으며 이 임시 실행 데이터는 Git에서 제외한다. 기존 갤러리는 `output/콜리더_게이트웨이/`에 그대로 있다.

## 경로와 장애물의 역할

- C1은 시작→첫 진입, 이후 C는 이전 진출→다음 진입이다. 실제 플래너의 leg는 C와 뒤따르는 G를 함께 포함하여 진출 차선까지 연결한다. 마지막 leg는 종료 도로의 종료 종방향 위치까지다.
- 체크포인트의 임의 차선을 목표로 삼지 않는다. XODR 교차로 연결의 실제 진출 차선들 중 이후 미션도 이어지는 대안을 목표로 쓴다.
- 게이트웨이 통과는 실제 진출 차선과 진행 방향의 `roadS`로 판정한다. 종료점도 도로 폭 전체의 종방향 위치로 판정하며, 기존 route.csv 종점이 먼저 가까워졌다고 완주 처리하지 않는다.
- `route.csv`는 기존 신호/횡단보도 등 법규의 경로 좌표 투영에 계속 필요하다. 새 모드에서는 게이트웨이 선택·복귀를 강제하는 기준 경로가 아니다.
- 사전 데이터는 **도로 연결**이다. 장애물 없는 것을 보증하는 주행 궤적이 아니다. 실제 궤적은 샘플점/검증된 합류·분기 곡선과, 도로 경계·실선·차량 충돌 검사를 통과한 5차 후보로 만든다. 원본 lane 중심점을 옆 차선으로 직선 연결하지 않는다.

## 주행 중 반복

현재 위치에서 활성 콜리더 및 게이트웨이를 거쳐 진출 차선까지 전역 후보를 생성한다. 수신된 정적 장애물은 거리 제한 없이 이 전역 탐색에 반영한다. `obstacle_trigger_maximum_distance: 70`은 로컬 회피 시작 탐색거리로 유지한다. 전방 현재 경로의 `obstacle_mandatory_avoidance_distance: 15`는 즉시 회피 판단용이다.

전역 A*는 초기화 때 복사한 별도의 지도/그래프를 이용하는 작업 스레드에서 실행된다. 제어 스레드는 완료 여부만 확인하며 기다리지 않는다. 계산 중에는 게이트웨이 연결을 고려한 기존 샘플 경로와 시간 예산이 있는 로컬 회피를 사용한다. 새 전역 경로는 다음 조건을 확인한 뒤 원자적으로 교체한다.

- 아직 같은 미션 leg·재계산 요청인지
- 현재 차량의 실제 위치/방향에 연결되는지
- 이미 지난 부분을 제외한 남은 경로가 최신 수신 정적 장애물과 겹치지 않는지

예상치 못한 정적/동적 객체가 현재 궤적을 막으면 로컬 후보를 다시 검사한다. 예측 충돌 검사를 통과한 후보가 있을 때만 기존 회피 경로를 교체한다. 신호·보행자 및 긴급제동 판단은 유지한다. 회피 목표 차선에 안착하거나 회피가 끝나면 그 위치부터 게이트웨이 전역 경로 재계산을 요청한다. 짧은 게이트웨이 정렬 후보가 이를 먼저 덮어쓰지 않게 했다.

실패 결과는 영구적인 경로 없음으로 보관하지 않는다. 객체 ID/위치/크기·방향, 차량 차선·진행 위치가 변하거나 재시도 시간이 지나면 다시 계산한다. 재계산을 요청했다고 기존 경로부터 비우지 않는다. 기존 경로를 보관하는 것은 안전 승인과 다르며 최신 충돌/제동 판단은 계속 적용된다.

## 감지 한계와 검증 상태

통신은 30개의 고정 객체 슬롯이다. 수신하지 않은 장애물을 복구할 수 없고, 미관측 영역은 안전 확인된 영역이 아니다. 이 저장소에서 실제 발행 측의 객체 우선순위 선정 소스는 확인되지 않았다. 30개 초과 시 가까운 위험 객체가 우선 전송되는지는 별도 확인이 필요하다. 여기서는 프로토콜이나 객체 수를 임의 변경하지 않았다.

M05–M14는 새 데이터 생성, C++ 로드, 모든 목표 진출 차선의 종방향 통과/인계 검사를 통과했다. M15의 홀수 체크포인트 미리보기는 정식 주행 입력으로 허용하지 않는다. 이 결과는 VTD 완주/장애물 회피/차량 동역학 검증이 아니다.

기본 corridor/수신 단위테스트는 통과했다. 기존 `controller_logic_tests::testCloseMovingLeadMayCommandStop`은 실패했다. 직접 호출하는 기존 behavior 코드가 가까운 이동 선행차에도 `minimumObjectResponseSpeed` 하한을 적용하는 것이 assertion과 충돌한다. 해당 behavior 함수/설정은 이번 수정에서 변경하지 않았으며 전체 안전 테스트 통과로 보고하지 않는다.

사용자 요청에 따라 이후 변경한 비동기 재계산·회피 후 재요청은 컴파일 확인까지만 하고, 추가 VTD 주행 검증은 하지 않았다.

주요 판단 로그: `async_search_started`, `async_route_adopted`, `async_stale_route_discarded`, `async_search_exhausted`, `post_avoidance_replan_requested`, `active_path_replaced`.

추가한 재현 단위테스트(이번에는 실행하지 않음): `build/corridor_lattice_tests --observed-global-replan`. 70m 밖에 수신된 정적 장애물 반영, 종료 종방향 목표, 회피 후 현재 차선에서의 비동기 재계산을 검사한다.
