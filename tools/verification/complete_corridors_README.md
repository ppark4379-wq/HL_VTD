# 전체 콜리더·게이트웨이 사전 생성 v2

[M05–M15 전체 그림 목록](index.html). 각 `Mxx/overview.svg` / `overview.png`가 시작부터 종료까지 전체 결과다. 기존 링크 호환을 위해 `topology.svg` / `topology.png`에도 같은 전체 그림을 넣었다. 새 출력에는 부분 확대 그림을 만들지 않는다. 이전 부분 결과와 구형 생성기는 정리했으며 이 패키지에 포함하지 않는다.

## 왜 이전 그림이 끊겼나

1. **이전 검수기는 전체 경로 생성기가 아니었다.** P2→P3, P4→P5 같은 교차로 쌍만 찾았다. 시작→첫 교차로, 교차로 진출→다음 진입, 마지막 진출→종료 사이에 다른 도로/교차로가 있으면 찾지 않고 경고만 남겼다. M09 시작·중간·끝, M10/M12/M13/M14의 중간 빈 곳은 이 누락이 직접 원인이었다.
2. **주어진 점들이 교차로의 실제 바깥 도로가 아니라 connectingRoad 안에 피팅된 경우가 많다.** 일반도로까지 거리만 비교하면 진출점이 들어온 도로에 다시 매칭될 수 있다. 예를 들어 M11 P5는 진입 R2811보다 실제 진출 R2806이 좌표에서 조금 더 멀다. 가까운 쪽만 고르면 한 블록을 돌아오는 잘못된 연결이 만들어질 수 있다. M13에서도 비슷한 방향 혼동이 생길 수 있다.
3. **기존 중심선 샘플은 일반 laneSection 끝점을 생략한다.** 이를 면 경계로 재사용해서 section마다 약 0.5m의 미표시 띠가 생겼다. 논리 연결 누락과 별개인 시각화 기하 문제다.
4. **기존 production의 route.csv 기반 allowedLanes와 진출 목표 캐시는 별도 문제다.** 이전 그림은 아직 차량에 적용하지 않은 검수안이었으므로, 그 빈 그림만으로 과거 정지/미완주의 원인을 확정할 수 없다. 과거 주행 원인을 확정하려면 당시 활성 corridor, 목표 lane, 실패한 edge와 로그를 대조해야 한다.

## 새 생성기의 입력과 원칙

사용자가 지정한 큰 구간 정의는 다음과 같다. **C1=P1(시작)→P2(첫 진입), C2=P3(이전 진출)→P4(다음 진입), … 마지막 C=마지막 진출→종료. G1은 P2가 속한 콜리더→P3가 속한 콜리더를 잇는 실제 차선 집합**이다. 그림의 C/G 번호는 이 기준을 따른다. 콜리더 사이에 실제 존재하는 작은 XODR junction은 구간 안의 내부 접속으로 채우며 추가 공식 G 번호로 혼동하지 않는다.

입력은 **원본 checkpoints.csv의 seq,x,y와 XODR의 실제 차선·폭·방향·연결**이다. route.csv와 기존 production의 체크포인트 lane 후보를 사용하지 않는다. 시나리오 번호나 특정 road ID에 따른 예외도 없다.

- CP는 도로 구역 식별 힌트다. 해당 좌표나 해당 차선을 의무 통과점으로 쓰지 않는다.
- 콜리더는 교차로 사이의 같은 방향 driving lane 면 전체다. road/section ID가 바뀌어도 일반도로 종방향 연결이 계속되면 같은 콜리더에 포함한다. 반대방향 차선을 섞지 않는다.
- 게이트웨이는 **진입 콜리더 차선들 → 실제 XODR 연결 차선들 → 진출 콜리더 차선들**의 대응 관계다. 하나의 점도, 임의의 CP 단면도 아니다. 여러 연결이 가능하면 여러 차선을 유지한다.
- 동일 콜리더의 모든 차선을 면으로 표시하는 것은 실선 차선변경 허용을 의미하지 않는다. 탐색에서는 기존 XODR 기반 합법 횡방향 edge만 사용한다. 교차로 내부 connector 간 횡이동으로 회전 분기를 바꾸는 edge는 사용하지 않는다.

## 생성 순서

1. XODR에서 일반도로 차선의 방향별 연결 성분(콜리더)을 구성하고 교차로 종방향 연결을 별도 보존한다.
2. 원본 좌표 주변 도로 면에서 콜리더 후보들을 만든다. 좌표가 교차로에 있으면 **해당 junction 영역 전체**의 링크를 보고 진입점은 upstream, 진출점은 downstream 일반도로 후보를 찾는다. CP 아래에 그려진 특정 회전 차선 하나를 고르지 않는다.
3. **P1→P2→…→종료의 모든 인접 순서**에 대해 차선 상태를 유지하는 단계별 Dijkstra 탐색을 수행한다. 각 점에서 독립적으로 가장 가까운 road를 골라 나중에 억지로 잇는 것이 아니라, 앞뒤 seq를 모두 연결할 수 있는 후보 조합을 선택한다. 규칙에 맞는 진입→진출 쌍 사이에는 실제 교차로 연결을 통과해야 한다.
4. 제공된 쌍 사이에도 중간 교차로가 있으면 제한 없이 찾는다. 찾은 전체 lane chain에서 일반도로 방문과 교차로 연결을 추출하고, 최종적으로 C=P1→P2/P3→P4… 및 G=P2→P3/P4→P5… 기준으로 묶는다. 내부 XODR 접속 개수와 공식 G 개수를 구분한다.
5. 같은 두 콜리더를 연결하는 다른 XODR 차선들도 찾는다. 다음 게이트웨이까지 이어질 수 있는지 종료부터 역방향 검사해, 도착은 되지만 이후 진행할 수 없는 대안은 게이트웨이 집합에서 제외한다.
6. 콜리더 전체 면을 칠하고 실제 gateway 연결 차선과 경계를 표시한다. 면의 section 끝점은 XODR의 해당 section 쪽 극한값으로 정확히 평가한다. 임의 직선 연결이나 이미지상 빈 곳 덧칠은 하지 않는다.
7. 전체 witness lane chain의 edge 존재, gateway 진입·진출 연결, 종방향 경계 기하 차이, 각 콜리더 차선의 다음 gateway 도달 가능성을 따로 기록한다.

## 출력 데이터

`Mxx/complete_network.json` (`topology.json`도 동일):

- `checkpoint_matches`: seq별 선택 콜리더, 도로 후보 근거, nearest road/section, 일반도로 면과 거리. 교차로 안의 CP는 일반도로까지 거리가 커도 곧바로 오매칭을 뜻하지 않는다.
- `corridor_components`: 방문 순서별 전체 lane-section 집합과 road ID 목록.
- `corridor_groups`: C1=P1→P2, C2=P3→P4…에 해당하는 콜리더 전체 면과 내부 접속 목록.
- `gateway_groups`: G1=P2의 콜리더→P3의 콜리더…에 해당하는 실제 차선 연결 묶음.
- `legs`: 게이트웨이별 source/target 콜리더, `entry_edges`, `connection_lanes`, `connection_edges`, `exit_edges`. 모든 key는 `[roadId, sectionIndex, laneId]`다.
- `intervals`: **모든 인접 CP 순서**의 연결 chain과 중간 road 목록. 처음/마지막도 누락하지 않는다.
- `witness_route`: seq 순서를 만족하는 연결 증명용 lane chain. 차량이 그대로 추종할 연속 궤적은 아니다.
- `witness_lateral_edges`: 증명 경로에 필요한 합법 차선변경 edge.
- `corridor_reachability`: 다음 게이트웨이/종료까지 graph 경로가 있는 차선과 없는 차선을 구분한다. 면 전체가 노랗다고 모든 위치에서 같은 행동이 가능한 것은 아니다.
- `geometry_gap_warnings`, `validation`: 그래프 연결과 기하·입력 규칙·차량 실행 가능성을 구분한 검증 결과.
- `centerline_step_warnings`: 면은 이어지지만 lane-link의 중심선 끝점이 옆으로 옮겨지는 경우. M06/M08의 R429 section4 lane1→section3 lane2에서 약 3.8m 차이가 확인됐다. 주변 동일 방향 콜리더 면은 겹쳐 이어지지만 이 중심점들을 그대로 직결하면 안 되고, 후속 합류 궤적 생성이 필요하다. 이를 면 단절과 구분해서 남겼다.

전체 요약은 `audit.csv` / `audit.json`에서 본다. 첫 콜리더 시작과 마지막 콜리더 끝은 시작/종료 CP의 도로 종방향 위치로 폭 전체를 잘라 표시한다(`surface_clips`, `surface_excluded_lanes`). 특정 차선이나 정확한 x/y 통과를 강제하는 것이 아니다. 교차로 경계는 실제 연결부를 사용한다. P는 도로 힌트이고 C/G는 위 큰 구간 기준의 번호, R은 road ID다.

## M15와 보장 범위

M15 저장본은 CP가 11개로, 시작+[진입·진출 쌍]+종료라는 규칙에 맞지 않는다. 이 경우 짝을 임의로 확정하지 않고 **일반적인 좌표 순서 연결 참고도**를 만든다. `checkpoint_rules_valid=false`이며 대회 규칙 검증 통과로 처리하지 않는다. 사용자 확인상 실제 시나리오도 없으므로 저장 데이터 참고용이다.

**잘못된 지도나 모순된 입력까지 무조건 연결을 만들어 성공 처리하지 않는다.** 일반도로 힌트 후보 범위 기본 30m, 거리·방향 점수와 XODR 연결 정확도에 영향을 받는다. 교차로에 매칭된 점은 해당 junction의 실제 인접 도로를 사용하므로 긴 연결곡선을 30m에서 끊지 않는다. 후보가 없거나 그래프가 단절되면 실패 단계와 원인을 반환한다. 이를 무시하고 가짜 edge를 추가하지 않는다.

전체 그래프가 이어졌다는 것은 **차량 폭·실선 변경 가능 구간의 길이·장애물·조향 곡률까지 검증 완료**했다는 뜻이 아니다. 현재 lateral edge는 해당 section 어딘가에서 차선변경이 허용되는지를 나타내므로 특정 시점에서 실행 가능한지는 후속 플래닝이 확인해야 한다. 회전교차로나 비표준 XODR junction 분류도 추가 지도에 대해 별도 회귀검사가 필요하다.

이번 수정은 **사전 콜리더·게이트웨이 생성 도구와 전체 시각화**에 적용했다. 차량의 mission_corridor.cpp, 신호·보행자·제어 로직은 변경하지 않았으며 새 산출물을 런타임에 연결하지 않았다. 따라서 기존 주행 문제가 이미 해결됐다고 주장하지 않는다.

## 재생성

```bash
cmake -S . -B build
cmake --build build --target export_mission_corridors -j4
python3 tools/verification/generate_complete_corridors.py
```

새 생성 명령은 geometry-only exporter를 호출해 XODR을 읽고 CSV 순서에 따라 사전 네트워크를 만든다. VTD 실행이나 route.csv가 필요하지 않다. Python 의존성은 numpy, PyYAML, PyQt5(QtSvg)다. 노면 배경인 XODR 기반 `road_map.svg`도 이 폴더에 함께 버전 관리한다. 따라서 저장소를 받은 뒤 별도의 무시된 precomputed_lane_network 폴더 없이 현재 지도로 재생성할 수 있다. XODR을 다른 지도로 교체한다면 배경도 같은 지도에서 다시 생성해야 한다. `provenance.json`에 입력/구현 해시가 기록된다.
